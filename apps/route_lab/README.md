# MaxMedia Route Lab

用于验证图片和视频原生压缩路线的 Flutter 实验应用。界面层只负责输入参数与展示
结果，`data` 层通过公共契约调用两个独立插件，方便后续替换执行器。

## 运行

```bash
flutter pub get
flutter run -d macos
```

当前界面通过系统文件选择器选取图片和视频，并自动在应用临时目录生成输出路径；
同时保留绝对路径输入用于调试。生产应用仍需补齐长期访问授权、相册写回和
security-scoped bookmark/SAF 持久化语义。

执行过程中会展示原生任务的真实进度。完成后默认显示可读的结果汇总，而不是直接
展示原始 JSON：

- 视频：原视频/压缩后视频独立播放预览，并对比文件大小、格式、分辨率、帧率、
  视频码率和时长，同时显示总耗时与体积减少比例；
- 图片：单图可选 JPEG、PNG、WebP 和平台支持时的 HEIC，默认用 WebP 质量 80
  和分享尺寸策略（等比缩小且不放大），也可选择保持原尺寸；原图/压缩后图片并排预览，并对比文件大小、格式、
  分辨率、质量参数、耗时与体积减少比例；推荐档最多编码两次，第二次复用已解码像素；
- 原始结果 JSON 保留在折叠区，便于开发排查和自动化取证。

视频界面的码率是上限，不再是无条件目标：当源视频码率更低时，插件会自动把
编码目标限制到源视频码率的 75%，并在结果中记录请求值与实际应用值。如果平台编码器
仍然生成了不小于源文件的结果，插件会删除该输出并明确提示“源视频已经高度压缩”，
避免把体积增加错误展示成压缩成功。需要进一步缩小这类视频时，应验证 HEVC 或降分辨率路线。
单视频和批量视频均可在分辨率档位之上选择标准、75% 或 50% 目标码率；默认仍是标准。
较低目标码率可能缩小输出，但会损失画面细节，不能视为同画质算法提效。
Apple 批量视频还可选择 HDR 兼容提示、显式转 SDR 或遇到 HDR 时拒绝 H.264。
批量结果保留 HDR 色彩风险提示；每条重复的码率估算技术说明只保存在原始结果中，
不会再以英文红字占据列表。

图片自适应策略属于 Lab 的“推荐档”规划逻辑，原生插件仍严格执行单次请求的质量和
尺寸参数，便于基准测试固定输入。多次尝试的编码耗时会合并计入结果总耗时；若降到
60% 仍不能减小文件，应用会删除无收益输出并给出提示。质量数字不能跨编码器直接
比较。WebP 在 Apple 平台由 libwebp 执行，当前会归一化像素方向，但不保留
EXIF/ICC 等 metadata；JPEG/PNG/HEIC 继续使用 ImageIO。缩放由界面请求明确指定，
原生插件不会自行改变尺寸策略。iOS/macOS Podfile 会在 Debug 构建中单独为 libwebp
启用编译优化，避免模拟器把未优化 C 编码器的耗时误当成产品性能。

WebP 保留 libwebp 默认编码档。较快档位在本机单样本中使文件增大约 4.2%，
不符合当前体积优先的目标；对照数据和复现步骤见仓库根目录的
`benchmark_results/evidence/2026-09-24-fast-webp/README.md`。

界面中的视频码率来自平台容器元数据，属于估算值；技术路线决策仍须使用
`ffprobe` 和 VMAF 等独立工具复核。Apple 视频路线会对“相同 codec 且源码率已经
低于目标”的含音频输入执行视频 sample 直通，只移除音频并重新封装，避免无收益的
解码重编码；结果 JSON 的 `videoProcessing` 会标记 `passthrough` 或 `transcode`。

## 测试

```bash
flutter analyze
flutter test
flutter test integration_test/native_routes_test.dart -d macos
```

集成测试样本会作为 Flutter assets 打包并复制到应用临时目录，因此测试不需要在
沙箱内启动 FFmpeg。样本身份与哈希登记在仓库根目录的 `fixtures/manifest.json`。
